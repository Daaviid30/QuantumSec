# Deploying QuantumSec

This guide explains how to prepare the environment, run QuantumSec locally, and host its current
frontend and backend for research use.

> [!IMPORTANT]
> QuantumSec is research and educational software, not a production-ready security product.
> The current HTTP application exposes the BB84 laboratory only; PQC, hybrid QKD–PQC,
> experiment-comparison, and AES-256-GCM endpoints are planned. Keys and results generated by the
> simulator must not be used as production cryptographic material. References to “production”
> below describe a persistent hosting topology, not a cryptographic assurance or certification.

## Architecture

QuantumSec consists of two services:

```text
Browser
   │
   ├── /             → React frontend built by Vite
   └── /api/*        → FastAPI backend served by Uvicorn
```

During development, Vite serves the frontend at `http://localhost:5173` and proxies `/api` to the
backend at `http://127.0.0.1:8000`.

In production, both components should be published under **the same domain**. A reverse proxy such
as Nginx serves the static frontend files and forwards `/api` to Uvicorn. This architecture matches
the current client, which makes all requests through relative paths such as `/api/health`.

## Requirements

| Tool | Version or configuration |
| --- | --- |
| Python | `3.14`, managed by `uv` |
| `uv` | Recent version |
| Node.js | `20.19+`, `22.12+`, or `24+` |
| npm | Included with Node.js |
| Git | Required to obtain the project and build `liboqs` |
| CMake | Required to build `liboqs` |
| C/C++ compiler | MSVC on Windows; GCC or Clang on Linux |

The `liboqs-python` wrapper is included in `pyproject.toml` and `uv.lock`. The Python package does
not include a precompiled copy of the native library: the first time `oqs` is imported, it may
automatically download and build a compatible version of `liboqs`. Git, CMake, and a compiler must
therefore also be available on the deployment machine.

## Preparing the PQC environment on Windows

This project uses
[`liboqs-python`](https://github.com/open-quantum-safe/liboqs-python), a Python wrapper for the
`liboqs` cryptographic library.

### Visual Studio Build Tools

Install **Visual Studio Build Tools** with the following workload:

- **Desktop development with C++**
  - MSVC C/C++ x64/x86 Build Tools
  - CMake Tools for Windows
  - Windows 11 SDK

Git and `uv` are also required. Python will be installed and managed through `uv`.

> [!TIP]
> `cl.exe` is not usually available in the global Windows `PATH`. Open the project from the
> **x64 Native Tools Command Prompt for Visual Studio** so that MSVC and the SDK are configured
> correctly.

```cmd
cd /d D:\path\to\the\project
code .
```

### Check the toolchain

Run the following commands in the same terminal:

```cmd
cl
cmake --version
git --version
uv --version
uv run python --version
```

The first command may finish with a message saying that no source files were provided. What matters
is that `cl` is recognized and displays the Microsoft compiler version.

After synchronizing the dependencies, force the native library to load for the first time:

```cmd
uv run python -c "import oqs; print('liboqs loaded successfully')"
```

This first run may take several minutes because `liboqs-python` downloads and builds `liboqs` when
it cannot find a compatible installation on the system.

### Add or update `liboqs-python`

The dependency is **already declared** in this repository, so a regular installation only needs
`uv sync`. Use the following command only when intentionally adding it to another branch or updating
the dependency declaration and lockfile:

```cmd
uv add liboqs-python
```

## Installing with `uv`

Run all Python commands from the **repository root**.

### Development environment

```bash
uv python install 3.14
uv sync --dev

cd ui/frontend
npm ci
```

`uv sync --dev` creates or updates `.venv`, installs the required Python version, and downloads the
main and development dependencies according to `uv.lock`. You do not need to activate the virtual
environment manually: `uv run` uses `.venv` directly.

### Production environment

```bash
uv python install 3.14
uv sync --frozen --no-dev

cd ui/frontend
npm ci
```

- `--frozen` prevents the server from modifying `uv.lock` during deployment.
- `--no-dev` omits tools that are only needed for testing and development.
- `npm ci` installs the exact versions recorded in `package-lock.json`.

## Running in development

The backend and frontend are separate processes. Start the backend first and keep both terminals
open.

### 1. Backend

From the repository root:

```bash
uv run uvicorn ui.backend.main:app --reload --host 127.0.0.1 --port 8000
```

Wait until `Application startup complete` appears, then check:

- API health check: <http://127.0.0.1:8000/api/health>
- OpenAPI documentation: <http://127.0.0.1:8000/docs>

The health endpoint response should include `"status":"ok"`.

### 2. Frontend

In another terminal:

```bash
cd ui/frontend
npm run dev
```

Open <http://localhost:5173>. Vite uses port `5173` in strict mode and proxies `/api` requests to
the backend on port `8000`.

## Pre-deployment checks

Run the backend suite from the repository root:

```bash
uv run pytest
uv run ruff check .
```

Then check the frontend:

```bash
cd ui/frontend
npm test
npm run typecheck
npm run build
```

The final command generates the static artifact in `ui/frontend/dist/`. You can inspect it locally
with `npm run preview`, but this preview server **must not be used in production**.

## Production deployment

The recommended setup is a Linux machine with Nginx in front of Uvicorn:

```text
Internet ── HTTPS ── Nginx
                       ├── /          → /var/www/quantumsec
                       ├── /api/*     → 127.0.0.1:8000
                       └── /docs      → 127.0.0.1:8000
                                      └── FastAPI / QuantumSec
```

Adapt the usernames, domain, and paths in the examples to the target server.

### 1. Prepare the backend

Clone the repository, enter its root directory, and install the locked dependencies:

```bash
git clone <REPOSITORY_URL> /opt/quantumsec
cd /opt/quantumsec
uv python install 3.14
uv sync --frozen --no-dev
uv run python -c "import oqs; print('liboqs loaded successfully')"
```

On Debian or Ubuntu, the usual prerequisites for building `liboqs` are:

```bash
sudo apt update
sudo apt install -y build-essential cmake ninja-build libssl-dev git
```

Test the production process without `--reload`:

```bash
uv run uvicorn ui.backend.main:app --host 127.0.0.1 --port 8000 --workers 2
```

Adjust the number of workers to the available CPU and memory. The backend binds to `127.0.0.1` so
that it can only be reached through the reverse proxy.

### 2. Run the backend as a service

Example `systemd` unit at `/etc/systemd/system/quantumsec.service`:

```ini
[Unit]
Description=QuantumSec FastAPI backend
After=network.target

[Service]
Type=simple
User=quantumsec
Group=quantumsec
WorkingDirectory=/opt/quantumsec
Environment=PYTHONUNBUFFERED=1
ExecStart=/opt/quantumsec/.venv/bin/uvicorn ui.backend.main:app --host 127.0.0.1 --port 8000 --workers 2
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Enable and check the service:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now quantumsec
sudo systemctl status quantumsec
curl http://127.0.0.1:8000/api/health
```

The `quantumsec` user must exist and have read and execute permissions for `/opt/quantumsec` and
`.venv`.

### 3. Build and publish the frontend

```bash
cd /opt/quantumsec/ui/frontend
npm ci
npm run build
sudo mkdir -p /var/www/quantumsec
sudo rsync -a --delete dist/ /var/www/quantumsec/
```

> [!CAUTION]
> `rsync --delete` removes files from the destination when they no longer exist in `dist/`. Use it
> only with the dedicated `/var/www/quantumsec/` directory after verifying the path.

You do not need to retain `node_modules` on the web server after publishing `dist/`, although it
will be required again to build future versions.

### 4. Configure Nginx

Example virtual host:

```nginx
server {
    listen 80;
    server_name quantumsec.example.com;

    root /var/www/quantumsec;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 10s;
        proxy_read_timeout 120s;
    }

    # FastAPI currently exposes its documentation outside /api.
    location = /docs {
        proxy_pass http://127.0.0.1:8000/docs;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location = /openapi.json {
        proxy_pass http://127.0.0.1:8000/openapi.json;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

Validate the configuration before reloading Nginx:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

Next, configure a TLS certificate so the domain is served over HTTPS. Only ports `80` and `443`
should be publicly exposed by the firewall; port `8000` should remain internal.

### 5. Final verification

```bash
curl --fail https://quantumsec.example.com/api/health
curl --fail https://quantumsec.example.com/
```

Also check the following in a browser:

1. The interface loads without errors.
2. The backend status appears as connected.
3. A BB84 simulation can be run successfully.
4. `/docs` displays the FastAPI documentation.

### Frontend and backend on separate domains

The current version is designed to use the same origin. If the components are deployed separately,
the following changes are required first:

1. Make the client's base URL configurable, as it currently uses relative `/api` paths.
2. Add the frontend's exact HTTPS origin to `allow_origins` in `ui/backend/main.py`.
3. Avoid `*` in CORS for a public deployment and allow only the required methods and headers.

## Updating a deployment

After downloading a new version, reinstall the locked dependencies, rebuild the frontend, and
restart only the backend:

```bash
cd /opt/quantumsec
git pull --ff-only
uv sync --frozen --no-dev

cd ui/frontend
npm ci
npm run build
sudo rsync -a --delete dist/ /var/www/quantumsec/

sudo systemctl restart quantumsec
curl --fail http://127.0.0.1:8000/api/health
```

Before running `rsync --delete`, confirm that `/var/www/quantumsec/` is the dedicated frontend
directory. If `pyproject.toml`, `uv.lock`, `package.json`, or `package-lock.json` change, do not
skip the synchronization steps.

## Troubleshooting

### `cl` is not recognized on Windows

Open the **x64 Native Tools Command Prompt for Visual Studio** and run the commands from there.
Also verify that the **Desktop development with C++** workload is installed.

### The first `oqs` import fails

Check the following in order:

```cmd
cl
cmake --version
git --version
uv run python --version
uv run python -c "import oqs"
```

The first import needs network access to download the `liboqs` source code when the library is not
already installed. In production, run this import during the build or preparation stage instead of
waiting for the first real request.

### The frontend reports that the backend is unavailable

1. Open `/api/health` first.
2. Confirm that Uvicorn was started from the repository root.
3. In development, verify that ports `8000` and `5173` are available.
4. In production, check `systemctl status quantumsec` and the Nginx logs.
5. Confirm that the proxy preserves the `/api/...` path when forwarding it to FastAPI.

### The backend works locally but is unavailable from the Internet

Uvicorn is expected to listen only on `127.0.0.1`. Public access should go through Nginx. Check DNS,
the virtual host, the TLS certificate, and the firewall rules. Do not expose Uvicorn directly except
during a controlled test.

### Port conflict during development

Vite is configured with `strictPort: true`, so it stops when port `5173` is already in use. Free the
port or update both the Vite port and the origins allowed by FastAPI CORS.
